# Plan: Hono Full-Stack Hello World

Build a minimal but complete Hono application demonstrating how the following pieces work together:

* Hono JSX for server-side rendering
* Hono SSG
* Dynamic Hono server routes
* `hono/jsx/dom` for client-side interactivity
* Vite for building/bundling
* Hono RPC for type-safe API calls

The goal is **not** to build a production application. The goal is to create a small application that makes the relationship between these features obvious when running and inspecting the generated output.

## 1. Project setup

Create a minimal TypeScript project using pnpm.

Use:

* Hono
* Vite
* TypeScript
* the Hono Vite integration/packages required by the current Hono documentation

Do not introduce React, Next.js, Astro, TanStack Start, or another frontend framework.

The application should run locally with a simple command such as:

```bash
pnpm dev
```

and have a production/build command such as:

```bash
pnpm build
```

Use the current Hono/Vite APIs rather than outdated examples.

## 2. Project structure

Organize the project so that server and client code are clearly separated.

For example:

```text
src/
├── server.ts
├── pages/
│   ├── Home.tsx
│   ├── Static.tsx
│   └── Dynamic.tsx
└── client/
    └── counter.tsx
```

The exact structure can differ if the current Hono/Vite setup recommends another structure.

Keep the project deliberately small.

## 3. Hono JSX server rendering

Create a Hono route:

```text
/
```

that returns an HTML document rendered using Hono JSX.

The page should visibly explain that it is server-rendered.

For example, display:

```text
Hono Hello World

This page was rendered by Hono JSX on the server.
```

Do not use React.

Make sure the generated HTML contains the actual markup rather than an empty client-side mount point.

## 4. Hono SSG

Add a separate route:

```text
/static
```

that demonstrates Hono SSG.

This page should contain obvious text such as:

```text
This page was generated at build time.
```

Configure the Hono SSG process so that this route is emitted as a static HTML file during the production build.

After running the build, make it possible to inspect the generated HTML file and verify that it is a real static document.

If Hono's current SSG API requires a particular configuration or adapter, follow the current official API rather than inventing an abstraction.

## 5. Dynamic server route

Create:

```text
/dynamic
```

This route must execute on the server for every request.

Make this obvious by displaying a value generated at request time, for example:

```text
Dynamic server page

Generated at: <timestamp>
```

Refreshing the page should produce a different timestamp.

Do not statically generate this route.

This should demonstrate the difference between:

```text
/static   → generated during build
/dynamic  → generated during request
```

## 6. Hono API route

Create an API endpoint:

```text
/api/hello
```

It should return JSON such as:

```json
{
  "message": "Hello from Hono",
  "timestamp": "..."
}
```

The timestamp should be generated by the server when the request is handled.

Define the API route in a way that allows its type to be exported for Hono RPC.

For example, expose an application type equivalent to:

```ts
export type AppType = typeof routes
```

Use the current recommended Hono RPC pattern.

## 7. Hono RPC client

Create a client-side module that uses:

```ts
hc<AppType>()
```

to call:

```text
/api/hello
```

Do not use `fetch()` directly for this request.

The TypeScript compiler should obtain the response/request types from the Hono server definition.

Make the example intentionally demonstrate that the client and server share the API contract.

If useful, add a small comment showing that changing the server response type is reflected in the client type.

## 8. `hono/jsx/dom` client component

Create a small interactive component using:

```ts
hono/jsx/dom
```

and Hono's JSX client-side functionality.

For example, create a counter:

```text
Counter: 0

[ Increment ]
```

Clicking the button should increment the counter without reloading the page.

Do not use React or another client framework.

The component should be bundled as client-side JavaScript by Vite.

## 9. Combine RPC and JSX/DOM

Make the client component also call the Hono API using Hono RPC.

For example, create a section:

```text
Server response

[ Call API ]

Message: ...
Server timestamp: ...
```

When the user clicks the button:

1. The `hono/jsx/dom` component handles the event.
2. It uses Hono RPC to call `/api/hello`.
3. The response is displayed inside the component.
4. The page does not reload.

This should demonstrate all three layers together:

```text
Hono server
    ↓
Hono RPC type
    ↓
client component
    ↓
hono/jsx/dom
```

## 10. Home page

Make `/` a small navigation/demo page containing links to:

```text
Hono Full-Stack Demo

[ Server-rendered page ]
[ Static SSG page ]
[ Dynamic server page ]
[ Client component + RPC demo ]
```

The home page itself should be rendered with Hono JSX.

Make the purpose of each page obvious so someone unfamiliar with the setup can understand the example by opening it in a browser.

## 11. Vite integration

Configure Vite so that:

* server-side Hono code is handled correctly
* client-side JSX/TypeScript is bundled
* `hono/jsx/dom` is included in the client bundle
* static assets are served correctly
* the production build produces the SSG output

Avoid unnecessary Vite plugins or abstractions.

The final project should use the smallest configuration that works with the current Hono/Vite integration.

## 12. Development vs production

Make the distinction between development and production explicit.

Verify:

```bash
pnpm dev
```

allows the application to be explored interactively.

Then verify:

```bash
pnpm build
```

creates the production/SSG output.

Document which routes are:

```text
Build time:
    /static

Server request time:
    /dynamic
    /api/hello

Server-rendered + client JavaScript:
    /

Client-side interactive:
    /client
```

Adjust this classification if the actual Hono/Vite architecture requires a slightly different arrangement.

### What to inspect

* View page source for Hono JSX server rendering.
* Inspect the generated build directory for the SSG HTML.

## 14. Verification

Before finishing, actually run:

```bash
pnpm install
pnpm build
pnpm dev
```

and verify all routes.

Test:

```text
GET /
GET /static
GET /dynamic
GET /api/hello
```

and verify that:

1. `/` renders HTML on the server.
2. `/static` exists in the generated SSG output.
3. `/dynamic` generates a fresh server-side value on each request.
4. `/api/hello` returns JSON.
5. The client component renders and responds to clicks.
6. The client component can call `/api/hello`.
7. The API call uses Hono RPC rather than raw `fetch`.
8. No React, Astro, Next.js, or TanStack dependency is introduced.
9. TypeScript compilation succeeds with no errors.

## 15. Final output

At the end, provide:

1. The complete project.
2. A short explanation of the architecture.
3. The commands needed to run it.
4. A table mapping each requested Hono feature to the file demonstrating it.
5. Any important limitations or caveats discovered while implementing the example.

Do not over-engineer the application. The primary goal is educational clarity: every requested feature should be easy to locate in the source code and easy to observe in the running application.
